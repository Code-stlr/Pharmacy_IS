# Weekly Project Status Check
**Information Systems Project Plan from Now to Week 15**

---

## Main Goal

By **Week 15**, every team must have a working information system that can be demonstrated. The project may be an application, website, software product, or another digital system that solves a clear user or organisation problem. The scope can be small, but the main process must work from start to finish.

---

## What Every Team Must Prepare Before the Next Practical Lesson

* Decide the current stage and status of your project.
* Prepare a short demonstration of what already exists.
* Show the technical or implemented part, not only slides or ideas.
* Write what each member has personally completed.
* Agree on one measurable task for every member before the next practical lesson.
* Give every task an owner, deadline, and clear result that can be checked.

---

## What You Will Show During the Weekly Check

| Team Report | Individual Report |
| :--- | :--- |
| Current project stage and project health | My responsibility in the project |
| What changed since the last check | What I personally completed |
| Working feature, prototype, data model, test, or other evidence | Evidence of my contribution |
| Current difficulty and team decision | What I will complete before the next lesson |
| Next team milestone | My deadline and expected result |

> **Important Rule:** A promise is not progress. Progress must be visible and measurable. You should be able to show the result, explain it, and connect it to your own work.

---

## Project Stages and What to Do Next

| Current Stage | What It Means | What the Team Should Do Next |
| :--- | :--- | :--- |
| **Planning** | The team has an idea but no clear scope or technical result yet. | Confirm the user problem, main process, requirements, roles, product scope, and first prototype. |
| **Started** | Some designs, documents, data models, or functions exist, but the main process does not work yet. | Build one small end-to-end process and show a visible result every week. |
| **Technical Foundation Exists** | The project has a prototype, database, architecture, or separate working parts. | Connect the parts, complete the core functions, and check data flow and user roles. |
| **Working System** | The main process works, but quality, errors, security, usability, or testing may be weak. | Test successful and unsuccessful cases, fix defects, improve security and user experience. |
| **Finished** | The agreed core product works and meets its acceptance criteria. | Improve quality, reliability, testing, documentation, deployment, analytics, or user value. |

---

## Project Status is Different from Project Stage

| Status | Meaning | What Must Be Shown |
| :--- | :--- | :--- |
| **On Track** | The next milestone is realistic. | Evidence, owner, deadline, and clear next action |
| **At Risk** | A problem may affect time, scope, quality, or users. | The cause, impact, response, and person responsible |
| **Blocked** | The team cannot continue without a decision, resource, access, or dependency. | The exact blocker, escalation action, owner, and recovery date |

## Examples of Measurable Next Tasks

* Create the registration screen and save a new user in the database.
* Design three connected database tables and explain the primary and foreign keys.
* Test five booking cases and record the result of each test.
* Interview two possible users and update three requirements based on their feedback.
* Add two user roles and demonstrate what each role can and cannot access.
* Prepare a deployment guide and run the system on another computer.

## Personal Contribution and Fair Expectations

### Every Member Must Own a Result
A team may divide the work in different ways. Programming is important, but it is not the only valuable contribution. Every student must produce evidence and understand how their work supports the whole information system.

| Student Role | Possible Measurable Contribution | What the Student Must Explain |
| :--- | :--- | :--- |
| **Developer** | Working feature, integration, error handling, deployment, or code improvement | What was built, how it works, what was tested, and what trade-off was made |
| **Data or Database Role** | Data model, tables, keys, validation, queries, data quality rules, or reports | How data moves, how integrity is protected, and who may access it |
| **UI or UX Role** | User flow, prototype, interface, accessibility check, or usability improvement | Which user problem is solved and what feedback changed the design |
| **Testing or Quality Role** | Test cases, defect log, acceptance test, security check, or user feedback | What failed, why it mattered, and what changed after testing |
| **Business Analyst or IT Manager** | Requirements, process model, priorities, acceptance criteria, risk decision, rollout, or stakeholder work | How the decision affects users, scope, quality, time, data, or implementation |
| **AI Assisted Development** | A generated feature that the student reviewed, changed, tested, and integrated | What AI created, what the student changed, how it was verified, and what limitations remain |

---

### Fair Expectations for Different Experience Levels

| Level | A Strong Result Can Be |
| :--- | :--- |
| **Beginning Student** | A small but complete feature or project task that the student can demonstrate and explain. |
| **Intermediate Student** | A useful project part connected to data, users, other functions, and meaningful testing. |
| **Experienced Student** | A deeper result with strong architecture, integration, security, reliability, performance, or maintainability. |
| **IT Manager or Analyst** | A measurable product result supported by requirements, user evidence, acceptance tests, decisions, risks, and enough technical understanding. |

## Week 15 Goal and Final Defence

### What "Finished" Means for This Course
* The system solves the agreed user or organisation problem.
* The main user process works from start to finish.
* Important data can be created, stored, changed, and used correctly.
* Key user roles and access rules are clear.
* The team has tested the main process and important error cases.
* The product can be demonstrated in a stable way.
* The team can explain current limitations and possible future improvements.
* Every member can prove and explain their own contribution.

### End Term and Final Defence
By Week 15, the project must be ready for the end term evaluation. During the final defence, your team will demonstrate the product and show why it is useful, relevant, working, and different from simple copies or ideas. You will show that you can plan, build, test, explain, and improve an information system.

### Prepare to Answer These Final Questions
1. What real problem does your system solve?
2. Who needs it and why?
3. What works now? Show it.
4. What is technically inside the system?
5. How does data move through the system?
6. What was tested and improved?
7. What did each member personally contribute?
8. What makes your solution useful or different?
9. What would you improve if you had more time?
